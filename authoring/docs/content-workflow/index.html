Six-stage golden path

How PEP content is built

Follow curriculum as it becomes accurate, usable, learner-ready content—then select any stage to inspect its proof.

JavaScript is off. The complete path is preserved below: all six stage records and every disclosure remain available with native HTML controls.

01

Input

Freeze what should be taught before learner files exist.

What happens
The approved curriculum slice, topic list, draft objectives, artifact applicability, honest minute budgets and version-specific official sources are fixed.
Why learners benefit
Content starts from the right sequence and source version instead of teaching an improvised or stale path.
What proves quality
Locked curriculum snapshots, hashes, intake evidence and an explicit source list make the starting point inspectable.

Linux Foundations: the worked path begins as a five-topic module mapped to the tracked curriculum.

Inputs → outputs

Locked curriculum and calendar snapshots become scoped manifests, draft objectives, applicability decisions, timing budgets and source-snapshot evidence.

Owner

A content planner or author proposes the intake. Later education and technology critics remain independent.

Tools + gates

pep new-topic; T01 schema, T14 timing and T19 curriculum integrity. Pending artifacts stay absent—never placeholders.

Failure / return

Unfrozen versions or timing overflow return here. The workflow reports the conflict; it does not compress honest minutes to pass.

02

Design

Give every course, module, topic and intended outcome one stable home.

What happens
Objectives, prerequisites, order and artifact choices become path-isomorphic course, module and topic manifests.
Why learners benefit
Each activity serves a named outcome, appears in the intended sequence and has no competing content copy.
What proves quality
Schemas, tree checks and explicit present-or-absent declarations keep catalog intent aligned with the learner tree.

Tools + gates

03

Build

Create one standalone learner experience and only the branches that earn their place.

What happens
artifact.html is authored first; declared Markdown, PDF, GIFT, video and lab branches follow where applicable.
Why learners benefit
The core page works offline, teaches before it tests and gives accessible feedback without a runtime dependency.
What proves quality
Artifact declarations, QA paths, deterministic companions and real-toolchain lab checks describe what the learner can actually do.

Linux Foundations: five topics produce 21 learner artifacts—5 HTML, 5 Markdown, 1 PDF, 5 GIFT and 5 video records.

Inspect branches, ownership and exact checks
Real branches only
  • Standalone Markdown, PDF and formative GIFT when declared.
  • A language-native lab only when authentic practice earns setup.
  • A video record only after verification.
  • Archify assets for authoring documentation only—never learner runtime.
Owner

One author context per module writes topics in order and runs local gates, but never approves its own output.

Tools + gates

Markdown/PDF derivation, GIFT validation and versioned components; T08–T13, T16, T18, T20 and T24 cover static behavior, offline use, sandboxing, accessibility, responsive layout and companion parity.

Failure / return

Network or sibling-file dependencies, inaccessible controls, dishonest simulation or placeholder companions return to authoring.

Prompt anchor, “authored” state and canonical sources
Tracked instruction

“An HTML learner page is one plain HTML file. It embeds all required CSS, JavaScript, data, and accessible visuals.” The authoring standard is tracked; no standalone author prompt or transcript is.

Authored means

Intended learner bytes exist, catalog declarations match them and required provenance is prepared. It does not mean accepted, approved or merged.

04

Verify

Bind claims to current sources and exercise the artifact as a learner will use it.

What happens
Source and optional video receipts are bound to artifact hashes; local tests check content structure, behavior, accessibility, timing and offline operation.
Why learners benefit
Technical guidance is current, interactions work, and the experience remains usable across devices and constraints.
What proves quality
Fresh source receipts, declarative QA paths and passing command exits prove more than a prose status claim.

Linux Foundations: five source receipts, five video receipts and five QA-path files bind the worked module to inspectable proof.

Inspect ownership, tools and exact checks
Inputs → outputs

Candidate bytes, manifests and official source sections become receipts with retrieval outcomes and SHA-256 bindings, plus deterministic test results.

Owner

The author prepares receipts and runs local gates. The technology critic independently checks claims; CI later repeats deterministic checks.

Tools + gates

check-links.mjs and check-video.mjs are explicit network commands. Normal checks stay offline. The 18-gate contract is implemented by 22 current T*.mjs modules.

Failure / return

Changed bytes stale receipts. Fix the authoritative input, regenerate derived files and rerun; never loosen thresholds to force a pass.

Prompt anchor, evidence and canonical sources
Tracked instruction

“Every technical claim traces to a source record … fetched live from official documentation with a retrieval date.” No generative prompt owns deterministic validation.

Evidence

sources.json, optional video.json, QA-path files, artifact hashes and command exits. Screenshots and traces remain ignored diagnostics or CI artifacts.

05

Review + improve

Apply independent teaching and technology judgment, then close accepted findings within a bounded loop.

What happens
Education and technology critics review the same final candidate; a non-author reconciles; the author corrects; relevant critics recheck fresh hashes.
Why learners benefit
Both how the material teaches and whether its technology is correct receive independent scrutiny.
What proves quality
Hash-bound reports, non-author decisions and same-role rechecks show who found, accepted and resolved each issue.

Linux Foundations: 7 accepted findings move from 5 resolved / 1 open after the first recheck to 7 resolved / 0 open after the second; no third cycle is used.

Inspect roles, loop rules and exact checks
Two independent lenses

Education checks objective alignment, teach-before-use, practice, feedback, cognitive load, timing and accessibility. The SME checks claims, commands, versions, fidelity, security and source freshness.

Accountable roles

Critics are independent of the author and each other. A non-author chooses accept, reject-with-evidence or escalate. The author fixes; the owning critic rechecks.

Bounded return

One correction loop runs at a time. A second is allowed once. Work escalates before a third loop rather than churning or self-closing.

Exact gate

T25 requires current education and SME coverage, reconciliation for every finding and zero open critical/high findings. Machine checks complement—not replace—judgment.

Prompt anchors, review state and canonical sources
Safe role anchors

Tracked workflow sections define both critic lenses and reconciliation vocabulary. No standalone critic or reconciler prompt file is tracked; hidden prompts and author transcripts are not inferred.

Independently reviewed means

Current education and SME evidence covers every reviewable file; each finding has a non-author decision; no critical/high item remains open. It does not imply all deterministic gates pass or approval exists.

06

Deliver

Reconcile the final record, earn approval and hand off without pretending the repository publishes.

What happens
Catalog declarations and evidence are reconciled, scope-local locks regenerate, a focused PR passes CI and approved material can be exported neutrally.
Why learners benefit
Only current, reviewable bytes move forward; platform conversion cannot silently create a competing source of truth.
What proves quality
Byte-identical locks, a green commit-bound CI result and human approval prove repository readiness. Platform acceptance remains separate.

Linux Foundations: its module lock inventories 74 tracked file records and preserves current versus historical evidence bindings.

Inspect locks, CI and neutral handoff
Catalog + locks

pep lock regenerates module.lock.json or course.lock.json. T04/T05 align declarations and files; T06 checks byte-identical regeneration; T25 rejects stale review coverage.

Focused PR + CI

A branch changes one module, course scope or tooling scope. CI runs npm test, migration check and npm run check; every merge still requires approval.

Neutral export

pep export and pep export-lab write ignored bundles under build/. Platform conversion, private assessment material, upload and publication stay outside this repository.

Failure / return

Stale bindings return to their owning evidence or review stage. Failed CI returns to the stage that owns the defect. Missing bundle files return to authoring.

What the five readiness words mean
Authored
Learner bytes exist, declarations match and provenance is prepared—not accepted, approved or merged.
Independently reviewed
Current dual-critic coverage, non-author decisions and no open critical/high—not a deterministic-gate or approval claim.
Delivery-ready
Final bytes pass applicable local gates; declarations, locks and review evidence are current; the focused PR is reviewable—not merged or uploaded.
Landed
The approved focused PR is merged to the default branch and merged-commit CI applies—not platform delivery.
Platform-ready
A neutral export exists and required private staging has been validated for handoff—not uploaded or accepted.
Prompt status, unavailable outcomes and canonical sources
Prompt status

No PR-writing, lock-generation or platform-adapter prompt is canonical. Tracked branch rules, CLI behavior and CI own this stage.

Unavailable outcomes

Platform upload, acceptance, publication and learner usage, completion or performance are not tracked here and are never converted into success claims.
