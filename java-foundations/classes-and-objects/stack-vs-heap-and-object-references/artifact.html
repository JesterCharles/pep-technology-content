        Stack frames and the heap

        Each method call gets a frame on the stack. The frame holds that call's parameters and local variables, and it disappears when the call returns. Every object made by new lives on the heap, together with its fields. A local variable of a class type holds only a reference: an arrow to an object on the heap.

        This is the model the Java Virtual Machine Specification describes. A running JVM may optimize where data really sits, but it never changes what your program can observe.

        On the job

        Decision: Share one object, or give each part of the code its own?

        Use it when: Every holder should see the same changes, like one shopping cart shown on two screens.

        → Choose something else when: One part must change its data without affecting another; make a second object with new and copy the fields.

        At work: A bug where changing one variable also changes another is often two references to one object; a memory diagram finds it.

        In interviews: Expect "stack versus heap" and "is Java pass-by-value?"

            Reachable or not

            An object is reachable while a chain of references leads to it from a variable that running code can still use, such as a local variable the running method will still use. When no such chain is left, the object is unreachable: no code can ever use it again, so it is eligible for garbage collection. The JVM reclaims its memory when it chooses, possibly never; you cannot force it.

            Reassigning a variable or setting it to null removes one reference: after Box p = new Box(); p = null; no variable reaches that box, so it is eligible. An object created by new but never stored has no reference at all.

            Another way to think about itOptional example

            Balloons at a fair are tied to strings that children hold. A child may let go of one string, but the balloon stays as long as anyone still holds a string tied to it. A balloon with no string held by anyone drifts off and is gone for good, whenever the wind happens to take it.

            Strings are references; a balloon nobody holds is unreachable, and when it leaves is not up to you.

                Java passes references by value

                Java passes every argument by value. For an object, the value copied into the parameter is the reference, so the method's parameter and the caller's variable point at the same object, but reassigning the parameter moves only the method's own copy.

                  Recap

                  • Each method call has a frame on the stack holding its parameters and local variables.
                  • Objects made by new, with their fields, live on the heap; reference variables hold arrows to them.
                  • Copying a reference makes two arrows to one object, so a change through either is seen through both.
                  • An object with no remaining chain of references is unreachable and eligible for garbage collection; the JVM decides when, if ever, to reclaim it.
                  Cheat sheet
                  Stack frameParameters and local variables of one call
                  HeapEvery object and array, with its fields
                  AliasBox b = a; gives two references to one object
                  Drop a referenceb = null; or reassign the variable
